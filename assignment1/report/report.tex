\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}
% =================================================

This study measures how the matrix size $n$ affects the execution time and memory use of the same basic
$i$-$j$-$k$ triple-loop matrix multiplication implemented in Python, Java and C. The three programs read identical
\texttt{float64} input matrices, produce bit-identical results, and were run with a documented protocol: shared inputs,
correctness tests, warm-up runs, five repetitions (three for runs of more than 20~s), median and interquartile range,
a 300~s time limit, and every process pinned to one performance core of a hybrid laptop processor. For
$n = 1024$ the median time of one multiplication was 72.8~s in Python, 1.19~s in Java and 2.37~s in C; Python could not
complete $n = 2048$ within the time limit, while Java and C needed 69.7~s and 32.2~s. The growth follows the cubic model
only while the data fits in the caches: for larger sizes the cost per multiply-add increases, and the fitted exponents
over $n = 256$--$2048$ are between 3.4 and 4.1. The contiguous C layout suffers a strong power-of-two effect
(going from $n = 1000$ to $1024$ multiplies its time by 3.6, against an expected 1.07), which the Java and Python layouts
do not show. A preliminary run without CPU affinity was up to 2.7 times slower and much more variable, showing that the
core assignment of a hybrid processor must be controlled. These conclusions are limited to the tested implementations,
settings and machine.

% =================================================
\chapter{Introduction and Objective}
% =================================================

Dense matrix multiplication is a basic building block of scientific computing, computer graphics and machine
learning. For two $n \times n$ matrices the straightforward algorithm performs $n^3$ multiply-add operations, so its
cost grows cubically with the matrix side $n$. Asymptotic complexity, however, says nothing about the constant
factors that determine the actual running time on a given machine. These depend on how the language executes the code
(interpretation, just-in-time or ahead-of-time compilation), how the matrices are stored in memory and how the
algorithm interacts with the memory hierarchy~\cite{leiserson2020,drepper2007}.

\section{Research question}

\textit{How does the matrix size $n$ affect the execution time and the memory use of the same basic triple-loop
matrix multiplication implemented in Python, Java and C, under fixed and documented execution conditions?}

The factors changed are the matrix size $n$ (the side of an $n \times n$ square matrix) and the implementation
language. The outcomes measured are the execution time of one multiplication and the peak memory of the process.

\section{Hypotheses}

The following predictions were stated before running the experiment:
\begin{enumerate}[label=\textbf{H\arabic*.}]
  \item For each language the execution time grows approximately as $n^3$, so doubling $n$ multiplies the time by about 8.
  \item Python is one to two orders of magnitude slower than Java and C, because the interpreter executes every operation on boxed objects.
  \item Java and C are within a small factor of each other once the JIT compiler has optimised the loop.
  \item Memory grows as $n^2$, with a fixed runtime overhead that is largest for Java and a per-element overhead that is largest for Python.
\end{enumerate}

\chapter{Background}
% =================================================

\section{The basic algorithm}

Given $A$ and $B$, each element of $C = AB$ is $C_{ij} = \sum_{k=1}^{n} A_{ik} B_{kj}$~\cite{golub2013}.
\Cref{alg:triple} shows the classic $i$-$j$-$k$ triple loop used in this study. It performs exactly $n^3$
multiplications and $n^3$ additions.

\begin{algorithm}[H]
\caption{Basic $i$-$j$-$k$ matrix multiplication}
\label{alg:triple}
\begin{algorithmic}[1]
\Require $A, B \in \mathbb{R}^{n \times n}$
\Ensure $C = AB$
\State allocate $C \in \mathbb{R}^{n \times n}$
\For{$i \gets 1$ \textbf{to} $n$}
  \For{$j \gets 1$ \textbf{to} $n$}
    \State $s \gets 0$
    \For{$k \gets 1$ \textbf{to} $n$}
      \State $s \gets s + A_{ik} \cdot B_{kj}$
    \EndFor
    \State $C_{ij} \gets s$
  \EndFor
\EndFor
\State \Return $C$
\end{algorithmic}
\end{algorithm}

\section{Memory access pattern}

In the $i$-$j$-$k$ order the innermost loop reads one row of $A$ sequentially and one column of $B$ with a stride of
$n$ elements. With row-major storage, each access to $B$ touches a different cache line, so for large $n$ most
accesses to $B$ miss in the cache~\cite{drepper2007,hennessy2017,lam1991}. When the row length is a power of two, the
elements of a column map to a small number of cache sets and can evict each other (conflict
misses)~\cite{drepper2007,lam1991}. Optimised libraries avoid these effects with blocking and
vectorisation~\cite{goto2008}; they are outside the scope of this controlled comparison and will be studied in
Assignment~2.

\section{Execution models}

CPython interprets bytecode; every \texttt{float} is a heap object, and every arithmetic operation involves dynamic
type dispatch and reference counting. Java code is first interpreted and then compiled at run time by the HotSpot JIT
compiler, which is why warm-up runs are recommended before measuring~\cite{georges2007}. C is compiled ahead of time
to native code. Leiserson et al.~\cite{leiserson2020} used this same triple loop to show differences of several orders
of magnitude between Python and C.

\section{Floating-point arithmetic}

Floating-point addition is not associative, so a different summation order can change the last bits of a result. For
an inner product of length $n$, the error with respect to the exact value is bounded by about
$n u \sum_k |A_{ik} B_{kj}|$, where $u \approx 1.1 \times 10^{-16}$ is the unit roundoff of
\texttt{float64}~\cite{higham2002}. Since all three implementations perform the same operations in the same order,
and Java uses strict IEEE~754 semantics by default since version~17~\cite{jep306}, they are expected to produce
bit-identical results.

\section{Implementations}

The three programs implement \Cref{alg:triple} with a scalar accumulator, use 64-bit floating-point numbers and do not
call any matrix library. They differ only in the unavoidable, idiomatic storage layout of each language
(\Cref{tab:impl}). All implementations are single-threaded. The C program creates no additional threads; the JVM
creates internal threads for JIT compilation and garbage collection, which in this study share the single core
assigned to the process.

\section{Inputs}

To guarantee that all languages multiply the same logical matrices, the inputs are generated once by
\texttt{generate\_inputs.py} and read by the three programs. For each size, $A$ and $B$ are drawn with NumPy's
\texttt{default\_rng} (PCG64) using seed $42 + n$, uniform values in $[0, 1)$, type \texttt{float64}, and stored as raw
little-endian row-major binary files. A manifest records the seed and the SHA-256 hash of every file.

The declared size sequence is $n \in \{64, 128, 256, 512, 1000, 1024, 2048\}$: powers of two, so that consecutive
sizes should differ by a factor of 8 in time, plus $n = 1000$ next to $1024$ to check whether the power-of-two size
has an effect of its own.

\section{Correctness checks}

Before benchmarking, \texttt{verify.py} runs every implementation on:
\begin{itemize}
  \item $1\times1$ and $2\times2$ matrices with known integer products (exact comparison);
  \item $AI = A$ and $A\,0 = 0$ for a random $8\times8$ matrix $A$ (exact comparison);
  \item random matrices with $n \in \{1, 2, 3, 17, 64, 100\}$, compared with \texttt{numpy.matmul} as the trusted
  reference using $\mathrm{rtol} = \mathrm{atol} = 10^{-12}$.
\end{itemize}
This tolerance is about 100 times larger than the error bound $n u$ for $n = 100$ and values in $[0,1)$ (no
cancellation is possible because all products are non-negative), but small enough to detect any indexing error. The
outputs of the three languages are also compared with each other bit by bit.

In addition, during the benchmark every multiplication returns a checksum: the sequential sum of all elements of $C$,
reported as the raw bits of the double. This guarantees that the result is consumed, so the compiler cannot remove the
computation, and allows checking that every repetition in every language produced the same result.

\section{Measurement protocol}

\begin{itemize}
  \item \textbf{Timer boundary (kernel measurement).} The timer covers only the multiplication function, including the
  allocation of the output matrix $C$ (an $O(n^2)$ cost, negligible compared with the $O(n^3)$ loop). Reading the
  input files, process start-up and the checksum are outside the timed region. Monotonic timers are used:
  \texttt{time.perf\_counter} (Python), \texttt{System.nanoTime} (Java) and \texttt{clock\_gettime(CLOCK\_MONOTONIC)} (C).
  \item \textbf{Processes, warm-up and repetitions.} Each (language, $n$) configuration runs in a fresh process that
  loads the inputs, executes the warm-up multiplications (not reported) and then the measured repetitions. Default:
  5 measured repetitions, with 3 warm-ups for Java (JIT compilation) and 1 for Python and C (caches and memory
  allocation). Costly configurations, defined as those whose predicted time (median of the previous size multiplied by
  $(n/n_{\text{prev}})^3$) exceeds 20~s, use 3 repetitions and 0 warm-ups (1 for Java), to keep the study feasible.
  For runs of minutes, the JIT compiles the loop during the first fraction of a second, so its effect is negligible.
  \item \textbf{CPU affinity and priority.} The processor is hybrid, and a probe that runs the same CPU-bound loop
  pinned to each logical processor (\texttt{core\_probe.py}, \Cref{sec:hybrid}) shows that the efficient cores are
  about 2--2.6 times slower than the performance cores. A preliminary run without affinity showed repetitions up to
  6.6 times slower than others of the same configuration. Therefore, every benchmark process is created already pinned
  to logical processor~12 (a performance core) with \texttt{HIGH} priority class. Because the JVM detects a single
  available processor, the garbage collector is fixed explicitly to the serial collector (\texttt{-XX:+UseSerialGC}),
  and JIT compilation shares the same core as the measured thread.
  \item \textbf{Budgets.} Maximum time of one multiplication: 300~s. Memory budget: 4~GiB per process. A configuration
  that exceeds a limit is stopped and recorded as a timeout or memory failure, and the larger sizes of that language
  are not attempted. No time is invented for failed configurations.
  \item \textbf{Summary statistics.} All raw measurements are kept in \texttt{raw\_measurements.csv}. Tables report the
  median, the first and third quartiles ($Q_1$, $Q_3$) and the interquartile range (IQR), computed with linear
  interpolation.
  \item \textbf{Memory metric.} Peak working set (peak resident memory) of the whole process, read with the Win32
  \texttt{GetProcessMemoryInfo} API after the process has finished. It includes the inputs, the result, temporary
  objects and the language runtime (interpreter or JVM), so it is not a measure of the matrix storage alone. To avoid
  measuring a launcher process, Java is started with the \texttt{java.exe} of the JDK. As a reference, the storage of
  three $n \times n$ \texttt{float64} matrices is $24n^2$ bytes.
\end{itemize}

\chapter{Results}
% =================================================

All the numbers in this chapter come from \texttt{results/raw\_measurements.csv}, \texttt{memory.csv} and
\texttt{summary.csv}, produced by \texttt{analyze.py}. Following common recommendations for reporting performance
measurements~\cite{hoefler2015}, the median is used as the central value and the interquartile range (IQR) as the
measure of variability.

\section{Correctness}

All 30 tests (10 cases $\times$ 3 languages) passed. The exact cases (known $1\times1$ and $2\times2$ products, identity
and zero matrix) gave exactly the expected values. For the random cases, the maximum absolute difference with respect
to \texttt{numpy.matmul} grew with $n$, as expected from the error bound, up to $2.1 \times 10^{-14}$ for $n = 100$, well
inside the tolerance of $10^{-12}$. The outputs of Python, Java and C were bit-identical in every test, and during the
benchmark every repetition of every language produced the same checksum for each size. Therefore the three programs
perform exactly the same floating-point operations in the same order, and the comparison is not affected by different
arithmetic. The GCC vectorisation report (\texttt{-fopt-info-vec}) confirms that the C loop was not vectorised; the
generated code uses scalar \texttt{mulsd} and \texttt{addsd} instructions.

\section{Limits}

No configuration exceeded the memory budget of 4~GiB; the largest peak was 431~MiB. The largest feasible tested size
was $n = 1024$ for Python and $n = 2048$ for Java and C. The largest attempted size was $n = 2048$ for all three
languages: the first Python multiplication with $n = 2048$ did not finish within the limit of 300~s and the process was
stopped, so no time is reported for it.

% =================================================
\chapter{Discussion}
% =================================================

\section{Does the time grow as \texorpdfstring{$n^3$}{n3}? (H1)}

Only partially. For small sizes the observed ratios are close to the cubic prediction of 8: Python from 64 to 256
(7.6 and 8.8), Java from 64 to 256 (9.3 and 9.4) and C from 128 to 256 (7.7). For larger sizes the time grows faster
than $n^3$: the cost per multiply-add increases (\Cref{fig:perop}) and the fitted exponents are between 3.4 and 4.1.
The algorithm still performs exactly $n^3$ multiply-adds, so the extra cost comes from the memory system, not from more
arithmetic.

This behaviour is consistent with the size of the working data relative to the caches. The innermost loop walks down a
column of $B$, so it touches one element of every row of $B$; while all of $B$ fits in a cache, these accesses are
relatively cheap. $B$ alone occupies 2~MiB for $n = 512$ (the size of the L2 cache of one performance core), 8~MiB
for $n = 1024$ (still inside the 24~MB L3 cache) and 32~MiB for $n = 2048$, which no longer fits in L3. The sharpest
increases appear exactly at these points: Java, whose cost per operation stays between 0.4 and 1.1~ns up to
$n = 1024$, jumps to 8.1~ns at $n = 2048$ (a ratio of 58 instead of 8), and C goes from 2.2 to 3.7~ns. In addition,
for $n = 2048$ each row of $B$ is 16~KiB long, so consecutive accesses of the inner loop always fall on different 4~KiB
memory pages, which increases address-translation (TLB) misses~\cite{drepper2007}. These explanations agree with the
data and with the literature~\cite{drepper2007,hennessy2017}, but hardware performance counters would be needed to
confirm them; they were not measured in this study.

\section{The power-of-two effect}

The most striking result is the comparison between $n = 1000$ and $n = 1024$. The cubic model predicts that 1024
should be only 7\% slower than 1000. Python (+2\%) and Java (+6\%) behave as predicted, but C becomes 3.6 times slower
(0.66~s to 2.37~s). A similar anomaly appears between $n = 64$ and $n = 128$, where C becomes 23 times slower while
Python and Java grow by about 8--9.

The C matrix is one contiguous block, so the distance between $B_{kj}$ and $B_{k+1,j}$ is exactly $8n$ bytes. When $n$
is a power of two, this stride is a power of two, and all the elements of a column fall into a few sets of the
set-associative cache, which evict each other even though the cache has plenty of free space (conflict
misses)~\cite{drepper2007,lam1991}. In Java, each row is a separate object with a header, so the distance between rows
is not exactly a power of two, and in Python the elements are pointers to objects scattered in the heap; neither layout
produces this regular pattern, which explains why they are not affected. The fact that C at $n = 1000$ is the fastest
of the three languages, and that it becomes the slowest at $n = 1024$, shows that the storage layout can matter as much
as the language itself.

\section{Python versus compiled languages (H2)}

Supported. Python is between 31 and 117 times slower than C and about 61 times slower than Java for $n = 1024$, in the
range of one to two orders of magnitude. Its cost of 33--36~ns per multiply-add for small sizes, compared with less
than 1~ns in Java and C, reflects the work of the interpreter for every iteration: reading bytecode, looking up the
types of the operands, creating a new \texttt{float} object for every intermediate result and updating reference
counts. This interpretation overhead dominates so strongly that Python does not show the power-of-two effect at all.
Its cost per operation roughly doubles from $n = 512$ onwards, when its matrices (about 32 bytes per element including
the float objects) no longer fit in the private caches. With a growth ratio of 8, a multiplication with $n = 2048$ would
need roughly 580~s, consistent with the observed timeout, although this value is a prediction, not a measurement.

\section{Java versus C (H3)}

Supported for $n \leq 1024$, where Java needs between 0.50 and 1.71 times the time of C, but not for $n = 2048$, where
Java is 2.2 times slower. Java was even faster than C for $n = 128$ to $512$ and $n = 1024$. For $n = 128$ and $1024$ this
is explained by the power-of-two effect on the C layout. For $n = 256$ and $512$, where C is about 1.4 times slower, the
reason is not established by this study: both programs execute a scalar loop with the same operations, but the machine
code generated by the HotSpot JIT compiler was not inspected, so differences in instruction scheduling, unrolling or
bounds-check elimination remain possible explanations. At $n = 2048$, every access to \texttt{B[k][j]} in Java first
needs the reference to row \texttt{k}, and the rows of $B$ are separate objects; when $B$ no longer fits in L3, these
extra dependent memory accesses may explain why Java degrades more than C, but again this was not measured directly.

\section{Memory (H4)}

Supported. For large sizes the peak working set grows approximately as $n^2$. C is very close to the storage estimate:
its baseline is about 4~MiB, and at $n = 1024$ and $2048$ it uses 27.9 and 99.9~MiB against 24 and 96~MiB of data. The
JVM needs about 42~MiB even for the smallest matrices, and at $n = 2048$ it reaches 320~MiB, more than three times the
data. Part of this is the heap of a garbage-collected runtime: every repetition allocates a new result matrix, and the
previous ones are released only when the collector runs; the input files are also read into temporary byte arrays.
Python uses about 6--7 times the size of the data at $n = 1024$, because each element is an 8-byte pointer to a separate
24-byte \texttt{float} object instead of an 8-byte value. The metric includes the whole process, so the comparison
mixes data and runtime overhead; it should not be read as the size of the matrices alone.

\section{Variability and the hybrid processor}

The preliminary run without affinity shows that, on a hybrid processor, the operating system can move a
single-threaded benchmark between core types with very different speeds. This made some medians more than twice as high
and some repetitions several times slower than others, which would have led to wrong conclusions (for example, Java
$n = 2048$ exceeded the time limit in that run). Pinning every process to a performance core removed most of this
variability: 14 of 20 configurations have an IQR below 10\%. The remaining variability is concentrated in the sizes
where the caches are under the most pressure ($n = 512$ to $1024$), which suggests interference from other processes
that share the L3 cache and memory bandwidth, and changes of the clock frequency under the \textit{Balanced} power plan.

\section{Limitations}

\begin{itemize}
  \item A single laptop was used, with the \textit{Balanced} power plan and normal background activity (including cloud
  synchronisation). Clock frequency and other processes could not be fully controlled.
  \item Each process was pinned to one logical processor, but the other hardware thread of the same core was not
  reserved, and no hardware performance counters (cache misses, TLB misses) were collected. The explanations based on
  the memory hierarchy are therefore supported by the timing patterns, not by direct measurements.
  \item Costly configurations used only three repetitions, so their IQR is less reliable.
  \item The memory metric is the peak working set of the whole process; it does not separate matrix storage from
  runtime overhead, and for Java it depends on when the garbage collector runs.
  \item The JIT-compiled code of Java was not inspected, so the reason why Java is faster than C for some sizes is not
  fully resolved.
\end{itemize}

% =================================================
\chapter{Conclusions}
% =================================================

Within the tested implementations, settings and machine, this study establishes that:
\begin{itemize}
  \item The same triple loop, with identical inputs and bit-identical results, needs 72.8~s in Python, 1.19~s in Java
  and 2.37~s in C for $n = 1024$. Python is one to two orders of magnitude slower than the compiled languages and could
  not complete $n = 2048$ within 300~s.
  \item The time follows the cubic model only while the data fits in the caches. Beyond that point the cost per
  operation grows, and the fitted exponents over $n = 256$--$2048$ are 3.4--4.1.
  \item The storage layout interacts strongly with the matrix size: the contiguous C layout is 3.6 times slower at
  $n = 1024$ than at $n = 1000$, an effect that the Java and Python layouts do not show. Consequently, no language is
  faster than another for every size: C was the fastest at $n = 64$, $1000$ and $2048$, and Java at $n = 128$--$512$
  and $1024$.
  \item Memory use grows as $n^2$; C stays close to the size of the data, while the JVM adds a fixed overhead and
  heap growth, and Python needs several times the size of the data because of boxed numbers.
  \item On a hybrid processor, controlling the CPU affinity is essential: without it, the results were up to 2.7 times
  slower and much more variable.
\end{itemize}

What remains unresolved is the exact cause of the differences between Java and C at $n = 256$, $512$ and $2048$, which
would require inspecting the generated machine code and collecting hardware counters. These results also motivate
Assignment~2: the cache effects observed here suggest that loop reordering and blocking should reduce the cost per
operation of the basic algorithm.
